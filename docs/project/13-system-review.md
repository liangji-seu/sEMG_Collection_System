## 架构目标

1. 数据可靠：保存成功必须有可验证的写入和关闭结果；不把部分成功当整体成功，不静默覆盖失败文件。
2. 状态一致：会话准备、开始、停止、中断和恢复有唯一编排顺序；界面依赖后端确认进入下一阶段。
3. 资源有界：队列、慢连接、缓存、日志和大文件读取有明确上限；预览降载不能改变落盘数据。
4. 失败可恢复：错误保留阶段和原因，提供不完整收尾；失败既不能假成功，也不能只能靠强杀程序脱困。
5. 易维护：共享职责放入少量明确模块；删除被覆盖实现、无调用模拟接口和失效引用；保留可用入口与数据格式。

## 必须保持的数据契约

- BLE 时间轴由既有包计数器规则驱动；计数器复位、主机到包抖动和真实丢包不能随意混为一谈。
- 2kHz EMG 输出只包含真实 SD 样本，保持真实缺失导致的时间间隔；不补前值、不压缩时间轴。
- 对单一来源的每条输出：`channels[i] == bin[sd_frame_id[i] + sync_bin_align_offset]`，并应用明确的通道映射。多来源补救必须保留来源与局部坐标信息。
- `sync_status=synced` 只代表文件需要的所有设备完成并通过相应校验；缺 bin、缺必需 IMU、跳过或部分失败不能被另一设备的成功覆盖。
- 设备/传感器数量、活跃质量、数据缺失是不同概念；启发式质量诊断不能悄悄删除真实数据。
- 视频首末帧时间对应 `N-1` 个间隔；存在逐帧时间时优先使用逐帧时间。空数据窗口保持空，不能回退展示不相关时间段。

## 最终实现与兼容性说明

- 新增的小模块分别负责进程拥有权、H5排他事务、计数器规则及视频时间映射；保留 `npm start` 与 `python tools/hdf5_tool.py` 两个日常入口。
- 采集写入带文件token与严格序号，PUSH/REP共用发送顺序和关闭栅栏。提示事件也进入同一顺序，不能静默丢失。视频启动回复丢失后仍保留录像所有权，明确停止后才允许下一轮。
- `partial` 表示只有部分物理设备完成；`unverified` 表示已有处理结果，但缺完整验证证据。当前IMU的±3帧匹配属于启发式，保存置信度/歧义信息，不能据此显示整文件“已验证”。原始物理传感器数据始终保留，零值诊断不缩减传感器数量。
- IMU新输出增加 `valid`/`missing` 字段；大规模缺帧ID存放 `sync_quality/devN/imu_missing_frame_ids`，通过 `missing_frame_ids_path` 引用，避免HDF5属性尺寸上限。异常跨度会在分配前明确拒绝。
- 离线写入使用同目录副本，因此需要至少约一个原文件大小的可用空间；提交失败不替换旧文件。`.offline.lock` 是稳定的排他锁文件，正常保留；不通过删除锁文件处理占用。
- 视频压缩保留原AVI，先完整解码核对再原子发布MP4。跨多个H5的引用更新逐文件提交；中途失败明确报告partial，AVI与已验证MP4都保留，不声称多个文件具有跨文件原子性。
- 预览缓存各设备的时间列（百万行约8MB），仅读取可见EMG窗口及滤波padding；不再一次物化全部16通道。真实时间有回退/重复时提示先修复，不凭排序或行号掩盖。
- 紧凑EMG解析用约68字节/帧（uint32 ID+16×int32），不含读取文件临时内存。标量二分查找使用同dtype标量，防止NumPy隐式提升导致每次复制整条索引。实际持续运行性能仍由设备速率、磁盘和视频编码能力决定。
