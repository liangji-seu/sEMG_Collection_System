# 存储栅栏超时导致整轮 H5 无法收尾（2026-11-03 现场）

## 现象

现场（`C:\Users\admin\Desktop\10_30_采集系统`，Windows 版本较旧）离散手势第 1 轮
（15:56:46 开始，共 162 秒）结束时弹出：

```
采集已因故障停止。
原因: 数据栅栏未完成，文件保持打开
阶段: stopped
故障来源/代码: storage / storage_write_failed
H5: 失败: 数据栅栏未完成，文件保持打开
视频: 成功: 本轮录像已保存
设备链路: 成功: 已停止本轮BLE数据流 ...
```

H5 被拒绝关闭，整轮数据无法正常收尾。

## 日志证据

`server_20261103_073354`（本地时间 15:33–16:16）：

| 时间 | 事件 |
|---|---|
| 15:56:46 | 采集开始，`last_sent_sequence` 从 0 递增 |
| 15:59:26 | storage `CAPTURE_HEALTH_PROGRESS`: `sequences.received=9018, written=9018` |
| 15:59:29 | `close_before`: 引擎 `last_sent_sequence=10190`，pending=0 |
| 15:59:34 | `close` 被拒：`数据栅栏未完成，文件保持打开`（等待 5 秒后） |
| 15:59:39 | 重试一次，仍被拒；采集被判 `storage_write_failed` 停止 |

关账时 storage 落后 **1172 个批次 ≈ 18 秒数据**。同期存储处理速率：

| 会话 | storage 收批速率 |
|---|---|
| 15:36–15:44（成功） | 69–76 批/秒 |
| 15:56–15:59（失败） | 50–58 批/秒（开场 69 后持续下降） |

引擎侧发送约 **62.5 批/秒**（每 16ms 一批），于是在第二个会话里 storage 越落越远。
旧逻辑固定只等 5 秒，1172 批按 56 批/秒需要约 21 秒，必然超时。

## 排除项

- 磁盘：剩余 50.5 GB，`disk_full` 不成立；
- 数据写入错误：`write_error=null`，没有 `sequence gap` / `append failed`；
- BLE：两台手环全程 `丢帧: 0`（该机器 Windows 版本较旧，
  `RequestPreferredConnectionParameters` 返回 "property is not available"，
  但实际链路没有丢包）；
- 视频：左右两路 MJPEG 均正常收尾。

## 根因

storage 写入吞吐略低于引擎发送速率（现场 50–58 vs 62.5 批/秒），积压随采集时间增长；
关闭时用的"固定 5 秒栅栏"无法容纳积压，于是判失败并保持文件打开。

## 修复（`3387e6f`、`7942b0b`）

1. **栅栏按进度等待**：只要 `last_data_sequence` 还在推进就继续等；连续 15 秒没有
   进展才失败，总上限 240 秒。等待期间每 10 秒打印一次 `已处理/目标/积压`，
   现场可从日志判断是在推进还是卡死。
2. **减少每批 HDF5 元数据写入**：`imu*_hw_version` / `num_imus` 只在值变化时写，
   不再每批重复写 attr。
3. 回归测试：`tests/test_storage_barrier.py` 增加进度语义用例（持续推进成功、
   无进展失败、总量超时失败）。

按现场速率估算：1172 批积压会在约 21 秒内收完，只会让"保存"多等一会儿，
不会再丢整轮数据。

## 现场待办

1. 用新代码重新打包并替换现场程序（本次修在 `7942b0b`）；
2. 那个被保持打开的 H5 若进程已退出，用 `tools/h5_recovery.py` 修复/补写元数据；
3. 若要进一步降低积压，可把 BLE→engine 的发送节拍从 5ms 放宽到 20–30ms
   （同样的数据按更大批次入库，storage 每批开销不变、总批数减半），
   需现场验证后再改。
