# 左手（1 号槽位）周期性丢包排查（2026-10-30）

## 现象

两个手环同时采集时，**1 号槽位（左手）稳定丢包，2 号槽位（右手）0 丢包**：

| 运行 | 1 号槽位设备 | 1 号槽位丢包 | 2 号槽位丢包 |
|---|---|---|---|
| 19:59 会话 | C752（原左手） | 31356 帧（~22%） | 0 |
| 21:22 运行 | C752 | 2854 次跳号 | 0 |
| 21:29–21:49 运行 | C752 | 866 次跳号 | 0 |
| 22:01 运行（两只手环已对调） | **CCA6（原右手）** | 2124 帧（~35%） | **0** |

**手环对调后丢包仍留在 1 号槽位**，说明不是某只手环的硬件/固件/SD 卡问题。

## 丢失形态

- 每跳号一次丢 **12–14 个包**（约 72–84 帧，≈0.3 秒数据）；
- 跳号间隔中位数 **1.304 秒**（几乎全是 1.0–1.5 秒），非常规律；
- 对应约 25% 的采样被设备侧丢弃；
- 同期 `raw_dropped=0`、`解析缓冲区=0`、发送队列无溢出 → **不是上位机缓冲区丢的**；
- 右手 `回调间隔异常` 反而更多（57 次 vs 2 次），却没有丢包 → 也不是 asyncio 事件循环卡顿导致。

这种"规律性、每次 12–13 个包"的跳号，最像是**设备侧 BLE 发送缓冲被填满后成批丢弃**，
即 1 号槽位那条连接的可用空口时间/吞吐明显低于 2 号槽位。

## 还没区分的两种可能

1. **位置/RF**：左手离 PC/天线更远、被身体遮挡，链路质量差；
2. **槽位/连接顺序**：1 号槽位总是先连接，可能协商到更差的连接参数（连接间隔、MTU）。

用户这次"对调手环"只换了手环，没有改变"左手戴的设备接 1 号槽位"这一映射，
所以两种可能仍然混在一起。

## 区分实验（待手环上电后执行）

| 实验 | 配置 | 判据 |
|---|---|---|
| A 基线 | 左手腕手环接槽位 1，右手腕接槽位 2 | 复现：槽位 1 丢包 |
| B 软件换槽 | **左手腕手环接槽位 2，右手腕手环接槽位 1**（手环位置不动） | 丢包跟左手走 → 位置/RF；丢包留在槽位 1 → 槽位/连接顺序 |
| C 单设备 | 只把左手腕手环接槽位 1 | 仍丢包 → 与双连接竞争无关 |

诊断脚本：`tools/ble_link_diag.js`

```bash
node tools/ble_link_diag.js --slot1 <MAC> --slot2 <MAC> --seconds 60
node tools/ble_link_diag.js --slot1 <MAC> --seconds 60          # 单设备
```

脚本每 5 秒通过控制端 `status` 打印两个槽位的 `total/lost/丢包率/MTU/RSSI`。

## 已补的诊断信息

- 连接成功日志增加 `name / rssi / mtu`：
  `[Dev1] 连接成功: <MAC> name=... rssi=... mtu=...`
- `status` 响应新增 `mtu` 字段，前端/脚本可直接读取。

## 如果确认是位置/RF

- 把蓝牙适配器用 USB 延长线放到受试者前方，远离机箱和 USB 3.0 口；
- 关闭适配器"允许计算机关闭此设备以节约电源"，关闭 USB 选择性暂停；
- Wi-Fi 尽量用 5GHz，避免 2.4GHz 与 BLE 抢信道；
- 若仍是单侧差，考虑双适配器（左右各一条链路）。
